## Архитектура

Архитектурный профиль: личный (`general-architecture-principles`, разделы 0 и 11: сценарий может звать репозиторий, чистые функции — в `domain/util`, над сценариями — Orchestrator).

**Перед любым кодом в `bot/` — общие скиллы:**
- `general-architecture-principles` и `python-clean-architecture` — слои, UseCase/Scenario, модели, ошибки, DI, порядок в модуле;
- `aiogram-bot-architecture` — форма фичи бота: `domain` / `data` / `entry` (Presenter + UiState + BotHandlers) / `di`, `public.py`, `Bot` в конструкторе, фоновые задачи и уведомления;
- `python-architecture-guards` — машинные проверки и базовые линии;
- `aiogram-feature-refactor` — перевод старой фичи на эталон: по фиче за PR, не сквозными правками.

Старый код (модульные функции-хендлеры, `.invoke()` вместо `__call__`, `Bot` из `BotManager`) приводится к эталону по фичам; **новый и изменяемый код пишется сразу по правилам скиллов**. Эталонная фича ещё не выбрана; когда появится, она будет записана здесь и в проектном скилле.

## Структура и слои

```
bot/core/            общий код: config, di, entry, domain (константы, форматирование)
bot/util/            общие утилиты
bot/resource/        локали и Strings.py (генерируется, руками не править)
bot/feature/<имя>/
    entry/           хендлеры aiogram, сервисы, фильтры
    data/            репозитории, datasource, YDB, внешние API
    domain/          usecase, scenario, model, интерфейсы репозиториев
    di/              провайдеры dishka (<Фича>Provider.py)
```

Правила (проверяются машиной):

- `domain` ничего не знает об инфраструктуре (`aiogram`, `ydb`, `openai`, `boto3`, ...), а также о `data` и `entry`.
- Зависимости слоёв внутри фичи: `entry` -> `data` -> `domain` (обратных нет).
- `*.data` импортируется только из `di` и `main.py`; `entry`, `domain`, `core` работают через интерфейсы из `domain`.
- `data` чужой фичи недоступен (только через `domain` или `di`); `entry` чужой фичи - только через её `public.py` (и из `di`).
- `domain/util` - чистые функции: без репозиториев, шлюзов и вышестоящих слоёв домена; внутри домена `orchestrator` -> `scenario` -> `usecase`.
- Файлы не длиннее 500 строк.

Новый код: фича в `bot/feature/<имя>/{entry,domain,data,di}`; общее для всех фич - в `bot/core`.
Новая фича подхватывается шаблонами `bot.feature.*` в контрактах `.importlinter`: править их не нужно.
Структуру фичи (корень, `domain/`, `entry/`, имена в `repository/`) проверяет `test/architecture/FeatureStructureTest.py`.

## DI: где добавить зависимость

DI на dishka, контейнер не привязан к aiogram: `bot/core/di/container.py` (`create_container`) - единственное место сборки.

- Новый класс (репозиторий, use case, сервис): добавить в `provide_all(...)` провайдера своей фичи, `bot/feature/<фича>/di/<Фича>Provider.py`. Зависимости берутся из типов `__init__`.
- Scope: APP - YDB, репозитории, клиенты, состояние приложения; REQUEST - всё, что зависит от Strings/апдейта. Не клади в REQUEST финализаторы: фоновые задачи живут дольше апдейта.
- Общее для всех фич (YDB driver/pool, Strings) - `bot/core/di/CoreProvider.py`. Провайдеры фич друг друга не импортируют: нужный тип чужой фичи просто указывается в `__init__`.
- Хендлер получает зависимость как `x: FromDishka[Тип]` (auto_inject включён в `main.py` для обоих диспетчеров). Вне aiogram: `create_container(StandaloneI18nProvider())`, затем `async with container() as request: await request.get(ChatService)`.
- Тесты: подменять внешние границы провайдером с `provide(override = True)`, образец - `test/core/di/ContainerTest.py`.

## Ответ бота: отложенные шаги

Ответ состоит из шагов «прочитать -> печатает -> сгенерировать и отправить» (`business/domain/usecase/*StepUseCase`, диспетчер `HandleChatStepUseCase`).
Шаги ставятся в `DelayedTaskQueue` (порт в domain; адаптеры `business/data/queue`: `InMemory` и `Sqs`, выбор - `DELAYED_QUEUE_BACKEND`, по умолчанию memory).
Каждый шаг сверяет талон `StepTicket` (S1) и тихо завершается, если он устарел; `asyncio.Task.cancel` для отмены не используется. Паузы - `HumanDelays` (DEBUG_MODE_TYPING = 0).
Вход: `ProcessChatEventUseCase` (хендлеры, `ReminderService`). Приёмник сообщений SQS (S2/S6) должен вызвать `HandleChatStepUseCase.invoke(ChatStepPayload.from_json(body))`.

## Проверки и запуск

Зависимости: `pip install -r requirements-dev.txt` (точные версии; инструменты не входят в прод-образ). В облачной сессии хук SessionStart ставит их в `.venv` (Python 3.11, как в Dockerfile и CI) и добавляет `.venv/bin` в `PATH`.

| Что ловит | Команда | Конфиг |
|---|---|---|
| Направление зависимостей: слои фичи и домена, чистые domain и `domain/util`, `entry` и `data` чужой фичи | `lint-imports --no-cache` | `.importlinter` |
| Форма кода: структура фич, один `__call__` у UseCase/Scenario/Orchestrator, порядок в модуле, `TYPE_CHECKING`, длина файлов, потолки базовых линий | `python -m pytest test/architecture` | `test/architecture/*Test.py` |
| Сложность, число аргументов, запрещённые API, ненужные `noqa` | `ruff check .` | `pyproject.toml` |
| Типы | `mypy` | `mypy.ini` |
| Базовые линии не выше, чем в ветке спринта | `python -m scripts.baseline_ratchet` (`--base origin/sprint4`) | `scripts/baseline_ratchet.py` |
| Юнит-тесты | `python -m pytest test` | `pytest.ini` |

Всё то же самое выполняет CI (`.github/workflows/ci.yml`, отдельные обязательные джобы; храповик - джоб `guards`), он же гейт деплоя.
Хук Stop (`.claude/hooks/architecture-check.sh`) запускает `lint-imports`, тесты архитектуры и храповик и не даёт
завершить работу при нарушении; он молчит, если дерево чистое и все коммиты уже на origin, и не блокирует, если инструменты не установлены.

**На новый код `# noqa`, строки в `ignore_imports` (`.importlinter`), записи в `per-file-ignores` (`pyproject.toml`), секции `[mypy-...]` в `mypy.ini` и записи в `_LEGACY_*` не ставятся - нарушение исправляется в коде.** Если правило мешает нормальному коду, не обходи его: опиши в PR («Решения для ревью») и предложи правку правила (`python-architecture-guards`, раздел 4).

## Стиль кода

Форматирование — скилл `python-code-style`: при более чем одном параметре или аргументе каждый на отдельной строке, закрывающая скобка на своей, trailing comma. Тесты — `general-unit-testing-principles` и `python-unit-testing`, типы — `python-mypy`.

- `ruff format` не запускать: он ломает правило «каждый параметр на отдельной строке».
- Именованные аргументы везде, где язык позволяет; константы — в начале файла, не хардкодить в методах.
- Порядок в модуле: импорты, константы, публичное, приватное (`_name`); приватное по умолчанию (`python-clean-architecture`, раздел 5).
- Тексты пользователю - в `bot/resource/locales/ru/messages.ftl`, `Strings.py` перегенерировать (`bot/resource/GenerateStrings.py`).

## Экономия контекста

- Во время работы — тесты затронутых модулей; полный набор один раз в конце: `python -m pytest test -q | tail -5` и список `FAILED`. Для импорта конфига нужны фиктивные переменные окружения — набор в шаге `pytest test` из `.github/workflows/ci.yml`.
- mypy — по изменённым файлам (`mypy <файлы>`).
- Сначала `grep -n` по символу, потом читать найденный диапазон; файл целиком — если он меняется в задаче.
- Падает незнакомый тест вне диффа — сначала поиск в Jira по имени файла, потом проверка этого файла на чистом HEAD.
